API для извлечения текста из файлов различных форматов, предназначенный для создания векторных представлений (embeddings) в системах RAG (Retrieval-Augmented Generation).

## Особенности

- 🔧 **Широкая поддержка форматов**: PDF, DOCX, PPT, изображения, таблицы, исходный код и многое другое
- 💻 **Поддержка исходного кода**: Более 50 языков программирования и форматов конфигурации
- 🖼️ **OCR**: Распознавание текста на изображениях (русский и английский языки)
- 📦 **Обработка архивов**: Извлечение текста из файлов внутри архивов с таймаутом 300 секунд (ZIP, RAR, 7Z, TAR и др.)
- 🌐 **Веб-экстракция с JavaScript**: Извлечение текста с современных веб-страниц с поддержкой SPA и lazy loading (Playwright + Chromium)
- 🎭 **Base64 изображения**: Автоматическое извлечение и OCR встроенных base64-изображений из веб-страниц
- 🔄 **Умная lazy loading**: Безопасный скролл для активации ленивой загрузки с защитой от бесконечных лент
- 🚀 **Асинхронная обработка**: Неблокирующее выполнение с поддержкой множественных worker-процессов
- 📊 **Структурированный вывод**: Объединение текста из разных источников
- 🔒 **Безопасность**: Защита от path traversal, подделки типов файлов, DoS-атак и SSRF
- 🐳 **Docker**: Готовый к развертыванию контейнер
- 📝 **Автодокументация**: Swagger UI интерфейс
- 🧪 **Комплексное тестирование**: Unit, integration и функциональные тесты
- 💾 **Полное извлечение**: Полное извлечение из DOCX (с колонтитулами, сносками, комментариями) и PPTX (с заметками спикера)
- 📋 **Base64 поддержка**: Обработка файлов в формате base64 через JSON API для интеграции с системами
- 🎙️ **Расшифровка аудио (новое в v1.12.0)**: Локальное распознавание речи (GigaAM v3, русский язык) с тайм-кодами сегментов и разметкой говорящих по каналам стерео-записей

### Коды ошибок

- `400` - Некорректный запрос (отсутствует Content-Length или неверный base64)
- `413` - Файл слишком большой (>20MB)
- `415` - Неподдерживаемый формат или несоответствие типа файла
- `422` - Поврежденный файл, пустой или защищенный паролем
- `504` - Превышен лимит времени обработки

### Настройки извлечения для веб-страниц (новое в v1.10.2)

API теперь поддерживает гибкие настройки извлечения текста с веб-страниц через параметр `extraction_options`. Все параметры **опциональны** и позволяют адаптировать процесс извлечения под конкретные требования.

#### Параметры настройки

**JavaScript и рендеринг:**
- `enable_javascript`: Включить Playwright для JS-рендеринга (по умолчанию: `false`)
- `js_render_timeout`: Таймаут JS-рендеринга в секундах (по умолчанию: `10`)
- `web_page_delay`: Задержка после JS в секундах (по умолчанию: `3`)

**Lazy Loading:**
- `enable_lazy_loading_wait`: Автоматический скролл для lazy loading (по умолчанию: `true`)
- `max_scroll_attempts`: Количество попыток скролла, 0 = без скролла (по умолчанию: `3`)

**Обработка изображений:**
- `process_images`: Обрабатывать изображения через OCR (по умолчанию: `true`)
- `enable_base64_images`: Обрабатывать base64 изображения (по умолчанию: `true`)
- `min_image_size_for_ocr`: Минимальный размер для OCR в пикселях (по умолчанию: `22500`)
- `max_images_per_page`: Максимум изображений на странице (по умолчанию: `20`)

**Таймауты:**
- `web_page_timeout`: Таймаут загрузки страницы в секундах (по умолчанию: `30`)
- `image_download_timeout`: Таймаут загрузки изображений в секундах (по умолчанию: `15`)

**Сетевые настройки:**
- `follow_redirects`: Следовать редиректам (по умолчанию: `true`)
- `max_redirects`: Максимум редиректов (только для requests)

**User-Agent:** Используется параметр `user_agent` на корневом уровне запроса.

### Выбор эндпоинта

**Используйте `/v1/extract/file`** когда:
- Загружаете файлы напрямую через форму или drag&drop
- Работаете с локальными файлами
- Интегрируетесь с файловыми системами

**Используйте `/v1/extract/base64`** когда:
- Файл уже закодирован в base64 в вашей системе
- Интегрируетесь с API, которые передают файлы в base64
- Работаете с микросервисной архитектурой через JSON
- Файл хранится в базе данных в виде base64

**Используйте `/v1/extract/url`** когда:
- Извлекаете текст напрямую с веб-страниц
- Работаете с современными веб-приложениями (SPA)
- Нужен контроль над процессом извлечения (JavaScript, lazy loading, изображения)
- **Скачиваете и обрабатываете файлы по URL (новое в v1.10.3)**
- Работаете с прямыми ссылками на документы, PDF, архивы и другие файлы
- Интегрируетесь с системами где файлы доступны через HTTP/HTTPS ссылки

**Используйте `/v1/transcribe`** когда:
- Нужна расшифровка аудиозаписи (звонки, совещания) с тайм-кодами
- Запись стерео и нужно знать, какая реплика чья (метки каналов)
- Нужна обработка без отправки аудио во внешние сервисы

## Расшифровка аудио (`/v1/transcribe`, новое в v1.12.0)

Эндпоинт принимает аудиозапись и возвращает расшифровку речи с тайм-кодами сегментов. Распознавание работает локально, без внешних сервисов: модель [GigaAM v3](https://github.com/salute-developers/GigaAM) (русский язык, с пунктуацией) запечена в образ, интернет в рантайме не нужен.

### Запрос

```bash
curl -X POST http://localhost:7556/v1/transcribe \
  -H "X-API-Key: <ключ, если включён AUTH_MODE=apikey>" \
  -F "file=@call.mp3" \
  -F "channel_labels=client,operator" \
  -F "external_id=rec-123"
```

| Поле формы | Обязательно | Описание |
|---|---|---|
| `file` | да | Аудиофайл: `mp3, wav, ogg, opus, flac, m4a, aac, wma, amr`. **Формат определяется по содержимому**. Неверное или отсутствующее расширение и неточный Content-Type клиента не мешают обработке поддерживаемого аудио |
| `channel_labels` | нет | Метки каналов стерео через запятую: первая метка — канал 0, вторая — канал 1. Всего до 256 символов, каждая метка до 64 |
| `external_id` | нет | Ваш идентификатор записи (до 128 символов), возвращается в ответе без изменений |

В режиме разработки (`make up`) тот же эндпоинт доступен на порту 7555. В продакшене запрос на порт 7555 тоже работает: основной сервис пересылает его в отдельный сервис `api-audio` (порт 7556), см. ниже.

Лимиты по умолчанию: размер аудиофайла 100 МиБ (`MAX_AUDIO_FILE_SIZE=104857600`), длительность 30 минут (`MAX_AUDIO_DURATION_SECONDS`), таймаут обработки 900 секунд (`TRANSCRIPTION_TIMEOUT_SECONDS`). Ограничение документов `MAX_FILE_SIZE` остаётся 20 МиБ. Режим синхронный: ответ приходит после окончания расшифровки. Таймаут клиента должен учитывать не только время обработки, но и ожидание слота и загрузку файла.

`Content-Length` обязателен. Авторизация, проверка заголовков и получение слота выполняются до чтения тела. Общий размер тела ограничен `MAX_AUDIO_FILE_SIZE` + 64 КиБ на multipart, в том числе при ложном `Content-Length`; отдельный файл ограничен `MAX_AUDIO_FILE_SIZE`. Загрузка ограничена `PROCESSING_TIMEOUT_SECONDS` (по умолчанию 300 секунд). До разбора формы имя файла неизвестно: в раннем ответе с ошибкой `filename` равен `unknown_file`. Ожидающие слот запросы не читаются и не занимают рабочие потоки; очередь ограничена `TRANSCRIPTION_MAX_QUEUE_SIZE`.

Реализация и проверка обмена со стороны 1С выполняются в отдельной задаче. Здесь проверяется приём и обработка запросов API, включая полный цикл HTTP-транскрибации.

### Ответ

```json
{
  "status": "success",
  "filename": "call.mp3",
  "external_id": "rec-123",
  "duration": 183.4,
  "channels": 2,
  "detected_format": "mp3",
  "model": "gigaam-v3-e2e-rnnt",
  "language": "ru",
  "text_status": "ok",
  "text": "Добрый день, компания «Ромашка». Здравствуйте, у меня вопрос.",
  "segments": [
    {"start": 0.52, "end": 3.10, "speaker": "operator", "channel": 1, "text": "Добрый день, компания «Ромашка»."},
    {"start": 3.40, "end": 5.85, "speaker": "client", "channel": 0, "text": "Здравствуйте, у меня вопрос."}
  ]
}
```

- `segments` отсортированы по `start`, время в секундах от начала записи.
- `detected_format` — определённый по содержимому канонический формат: OGG с Opus обозначается `opus`, контейнер MOV/MP4 с аудиодорожкой — `m4a`. Исходное имя сохраняется в `filename`: например, файл с именем `recording.ogg` и фактическим содержимым M4A получает `detected_format: "m4a"` без переименования.
- **Кто говорит.** Если запись стерео (МИКО умеет писать звонки в стерео с раздельными каналами), каждый канал распознаётся отдельно, а `speaker` берётся из `channel_labels`. Без меток подставляются `channel_0` и `channel_1`. Для моно (и для записей с тремя и более каналами, которые сводятся в моно) `speaker` и `channel` равны `null`. Так же обрабатывается моно, сохранённое как стерео (каналы совпадают): оно распознаётся один раз, иначе каждая реплика пришла бы дважды с двумя разными говорящими. Какой канал соответствует клиенту, а какой оператору, зависит от настроек вашей АТС; проверьте это на пробной записи.
- **Речи нет.** Если речь не найдена, ответ `HTTP 200` с `"text_status": "no_speech"`, пустыми `text` и `segments`. Это не ошибка.
- **Речь не распознана.** Пустой результат основной модели повторно проверяется GigaAM v3 e2e CTC int8. Если обе модели вернули пустой текст, речевой сегмент остаётся в `segments` с исходными тайм-кодами и `text: ""`. `text_status` равен `partial`, если часть речи распознана, или `unrecognized`, если не распознано ни одного сегмента. Все эти статусы возвращаются с HTTP 200; поле `text` объединяет только непустые тексты. Поле `model` обозначает основную модель контура.
- Результат связан с исходным файлом через `filename` и `external_id`.

### Ошибки

Ошибки приёма и обработки: `{"status": "error", "filename": "...", "message": "..."}`. Ошибка авторизации `401` использует общую схему API: `{"detail": "API key required"}` или `{"detail": "Invalid API key"}`.

| Код | Когда |
|---|---|
| 400 | отсутствует или некорректен `Content-Length`; превышена длина `external_id` или `channel_labels` |
| 401 | нет или неверный `X-API-Key` (при `AUTH_MODE=apikey`) |
| 408 | истекло время загрузки аудиофайла |
| 413 | размер файла или длительность записи больше лимита |
| 415 | содержимое не является поддерживаемым аудио или формат невозможно определить |
| 422 | файл пустой или повреждён, нет аудиодорожки |
| 500 | непредвиденная ошибка сервера (подробности только в логах) |
| 503 | расшифровка отключена, модель недоступна или сервис занят (в последнем случае есть заголовок `Retry-After`, повторите запрос позже) |
| 504 | превышен таймаут обработки |

### Переменные окружения

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `ENABLE_TRANSCRIPTION` | `true` | при `false` модель не загружается, а эндпоинт отвечает 503 или, если задан `TRANSCRIPTION_UPSTREAM_URL`, пересылает запрос в `api-audio` |
| `TRANSCRIPTION_UPSTREAM_URL` | пусто | адрес `api-audio` (например, `http://api-audio:7556`); действует только при `ENABLE_TRANSCRIPTION=false`. В `docker-compose.prod.yml` для `api` задан по умолчанию |
| `TRANSCRIPTION_MODEL` | `gigaam-v3-e2e-rnnt` | модель [onnx-asr](https://github.com/istupakov/onnx-asr) |
| `TRANSCRIPTION_QUANTIZATION` | пусто | пусто = fp32, `int8` = компактные веса. Образ выставляет её сам по `GIGAAM_QUANTIZATION` при сборке; в `.env` не задавайте |
| `MODELS_DIR` | `/opt/models` | каталог с весами внутри образа |
| `MAX_AUDIO_DURATION_SECONDS` | `1800` | максимальная длительность записи |
| `MAX_AUDIO_FILE_SIZE` | `104857600` | максимальный размер аудиофайла: 100 МиБ, независимо от документов |
| `TRANSCRIPTION_TIMEOUT_SECONDS` | `900` | таймаут обработки |
| `TRANSCRIPTION_MAX_CONCURRENCY` | `1` | сколько распознаваний одновременно в одном процессе |
| `TRANSCRIPTION_QUEUE_WAIT_SECONDS` | `30` | сколько запрос ждёт свободный слот до ответа 503 |
| `TRANSCRIPTION_MAX_QUEUE_SIZE` | `2` | максимум запросов, ожидающих слот; `0` — отказывать сразу при занятости |
| `TRANSCRIPTION_THREADS` | число ядер хоста | потоки onnxruntime; в контейнере с лимитом CPU задавайте явно (для `api-audio` — из `.env`, иначе из `AUDIO_CPUS`) |
| `TRANSCRIPTION_VAD_MIN_SILENCE_MS` | `500` | минимальная пауза между сегментами речи |
| `TRANSCRIPTION_VAD_SPEECH_PAD_MS` | `300` | запас вокруг сегмента речи; сегменты делятся паузой не меньше `MIN_SILENCE + 2×PAD` (при 500/300 около 1,1 с) |

### Развертывание и подключение

Модель занимает память в каждом процессе, поэтому в продакшене запускаются **два сервиса из одного образа** (`docker-compose.prod.yml`):

| Сервис | Порт | Назначение |
|---|---|---|
| `api` | 7555 | документы, изображения, веб-страницы; `ENABLE_TRANSCRIPTION=false`, много воркеров; `/v1/transcribe` пересылает в `api-audio` |
| `api-audio` | 7556 | `/v1/transcribe`; один воркер, модель загружается один раз |

Клиенту достаточно одного адреса: `POST http://<сервер>:7555/v1/transcribe` обрабатывается так же, как запрос на 7556. Порт 7556 остаётся рабочим и годится для прямого доступа и мониторинга.

```bash
make prod-up                      # собирает образ и поднимает оба сервиса
curl http://localhost:7556/health # проверка сервиса расшифровки
```

- **Образ.** Веса основной GigaAM v3 (около 0,9 ГБ в fp32), резервной CTC int8 (около 230 МБ) и VAD скачиваются с Hugging Face при сборке, поэтому сборке нужен доступ в интернет. Для компактных весов основной модели укажите `GIGAAM_QUANTIZATION=int8` в `.env`: `docker-compose.prod.yml` передаст её в сборку обоих сервисов (вручную: `docker build --build-arg GIGAAM_QUANTIZATION=int8 -t text-extraction-api .`). Резервная модель всегда использует int8. `TRANSCRIPTION_QUANTIZATION` в `.env` не задавайте: несовпадение с весами в образе даёт 503 на каждый запрос при зелёном `/health`.
- **Ресурсы.** Ориентир по [документации МИКО](https://docs.mikopbx.ru/mikopbx/modules/miko/module-local-speech-to-text/docker-worker) для того же движка: от 4 ядер CPU (лучше 8 с AVX2), от 4 ГБ RAM. В проверке контейнера с лимитами 4 CPU / 4 ГБ синтетическая запись длиной 191 секунду дала 40 сегментов за 6,5 секунды, пиковая память процесса — около 1,5 ГБ; качество и скорость реальных звонков оцениваются отдельно. Обе модели прогреваются при старте. Лимиты контейнера `api-audio` задаются переменной `AUDIO_CPUS` (по умолчанию 4) и в `docker-compose.prod.yml`. Если на хосте меньше 4 ядер, Docker не запустит контейнер: укажите `AUDIO_CPUS` не больше числа ядер.
- **Готовность.** При старте модель прогревается, ошибка (например, нет весов) пишется в лог и не останавливает API. `GET /health?check=transcription` отвечает 200 только при загруженной модели и 503 иначе; именно его использует healthcheck `api-audio`. Обычный `/health` не изменился.
- **Загрузка браузера при сборке.** Если фильтрация HTTPS мешает доступу к `cdn.playwright.dev`, можно выбрать официальные адреса Google и Microsoft без отключения TLS: `docker build --build-arg PLAYWRIGHT_CHROMIUM_DOWNLOAD_HOST=https://storage.googleapis.com/chrome-for-testing-public --build-arg PLAYWRIGHT_DOWNLOAD_HOST=https://playwright.download.prss.microsoft.com/dbazure/download/playwright -t text-extraction-api .`. Параметры действуют только при сборке; без них Playwright использует свои стандартные адреса.
- **Пересылка с порта 7555.** Основной сервис проверяет ключ, `Content-Length`, размер и время загрузки, затем потоком, без буферизации в памяти, передаёт файл в `api-audio` и возвращает его ответ без изменений (статус, тело, `Retry-After`). Если `api-audio` недоступен, клиент получает `503` с `Retry-After`, если не ответил вовремя — `504`, если ответ некорректен — `502`; тело ошибки в обычном формате `{status, filename, message}`. Проба `GET /health?check=transcription` на 7555 показывает готовность модели в `api-audio`. Если клиент оборвал соединение, запрос к `api-audio` прерывается (в логе `499`), но уже запущенная расшифровка дорабатывается и до конца держит слот. Ключи `API_KEYS` и `AUTH_MODE` должны быть одинаковы в обоих сервисах: общий `.env` это обеспечивает.
- **Подключение 1С.** Адрес `http://<сервер>:7555/v1/transcribe` (или `:7556` напрямую), метод POST, тело `multipart/form-data`; при включённой авторизации заголовок `X-API-Key`. Обрабатывайте `503` с `Retry-After` повтором запроса и `504` как «запись слишком длинная или сервер перегружен». Передавайте `external_id` (например, идентификатор записи в МИКО), чтобы сопоставлять ответ с исходной записью.

## Безопасность

API включает несколько уровней защиты:

### 🛡️ Санитизация имен файлов
- Автоматическая очистка имен файлов от потенциально опасных символов
- Предотвращение атак типа path traversal (`../../../etc/passwd`)
- Использование безопасных имен для внутренней обработки

### 🔍 Проверка типов файлов
- Верификация соответствия расширения файла его реальному содержимому
- Использование MIME-типов для определения истинного формата
- Предотвращение загрузки исполняемых файлов под видом текстовых

### 🚫 Защита от DoS-атак
- Обязательная проверка наличия заголовка `Content-Length`
- Предотвращение загрузки файлов неизвестного размера
- Ограничение максимального размера файла (20MB)

### 🗜️ Защита от zip-бомб
- Ограничение размера распакованного содержимого архивов (100MB)
- Контроль глубины вложенности архивов (максимум 3 уровня)
- Изоляция процесса распаковки с таймаутом

### 📋 Логирование безопасности
- Детальное логирование всех попыток нарушения безопасности
- Предупреждения о подозрительной активности
- Трассировка потенциальных угроз

### 🔑 Аутентификация (опционально, новое в v1.11.0)

API поддерживает простую API-key аутентификацию через переменные окружения:

```bash
# Без аутентификации (default — открытый API)
AUTH_MODE=none

# С аутентификацией: требуется заголовок X-API-Key
AUTH_MODE=apikey
API_KEYS=secret-key-1,secret-key-2  # несколько ключей через запятую (ротация)
```

Защищаются эндпоинты `/v1/extract/*` и `/v1/supported-formats`. `/health` и `/` остаются открытыми (необходимо для Docker healthcheck без секретов).

```bash
# AUTH_MODE=apikey — требуется заголовок
curl -H "X-API-Key: secret-key-1" -F "file=@doc.pdf" http://localhost:7555/v1/extract/file
```

Коды ответов: `401 — API key required` (нет заголовка) / `401 — Invalid API key` (неверный).

В **Swagger UI** (`/docs`) при `AUTH_MODE=apikey` появится кнопка **"Authorize"** в правом верхнем углу — введите ключ один раз, и он будет автоматически добавляться ко всем запросам. В **ReDoc** (`/redoc`) ключ описан в секции **"Authentication"**.

### 🌐 SSRF и редиректы (улучшено в v1.11.0)

При извлечении текста с URL:
- Блокируются внутренние IP-диапазоны (`BLOCKED_IP_RANGES`) и хосты (`BLOCKED_HOSTNAMES`).
- По умолчанию `follow_redirects=False` — сервис не следует HTTP-редиректам без явного запроса в `extraction_options`.
- Если редиректы включены явно, каждый final_url повторно проверяется через SSRF-фильтр (защита от DNS rebinding и chained-SSRF).
- Жёсткий верхний предел: `max_redirects ≤ 10` независимо от пользовательского значения.

## Производительность

### Ограничения

- **Максимальный размер файла**: 20 MB
- **Максимальный размер архива**: 20 MB
- **Максимальный размер распакованного содержимого**: 100 MB
- **Таймаут обработки**: 300 секунд (5 минут) для всех операций
- **Таймаут обработки архивов**: 300 секунд (5 минут) с принудительным завершением
- **Максимальная глубина вложенности архивов**: 3 уровня

### Оптимизация

- **Асинхронная обработка**: Все CPU-bound операции выполняются в отдельном пуле потоков
- **Неблокирующая архитектура**: Event loop не блокируется при обработке тяжелых файлов
- **Множественные worker-процессы**: Настраиваемое количество процессов для продакшена
- **Изоляция операций**: Сбой в одной операции не влияет на другие

**Рекомендации:**
- Используйте правильные форматы файлов
- Сжимайте изображения перед отправкой
- Для продакшена установите `WORKERS=9` (или 2 * количество ядер CPU + 1)
- Убедитесь в наличии заголовка Content-Length в запросах

### Статистика обработки

| Тип файла | Среднее время обработки | Особенности |
|-----------|------------------------|-------------|
| Текстовые файлы | <1мс | Автоопределение кодировки |
| Исходный код | <1мс | 50+ языков программирования |
| Изображения (OCR) | 100-500мс | Русский и английский |
| PDF документы | 50-200мс | С OCR для изображений |
| Office документы | 100-1000мс | Полное извлечение |
| DOCX документы | 100-800мс | Включая колонтитулы, сноски, комментарии |
| PPTX презентации | 100-600мс | Включая заметки спикера |
| Таблицы (большие) | 100-300мс | Все популярные форматы |
| Архивы | 200-2000мс | Таймаут 300 секунд |

## Архивы

### Поддерживаемые форматы архивов

- **ZIP**: Стандартный формат, быстрая обработка
- **RAR**: Требует библиотеку rarfile
- **7Z**: Требует библиотеку py7zr
- **TAR**: Включая сжатые варианты (GZ, BZ2, XZ)

### Обработка архивов

1. **Распаковка**: Архив распаковывается во временную папку
2. **Фильтрация**: Игнорируются системные файлы (.DS_Store, Thumbs.db)
3. **Обработка**: Каждый файл обрабатывается согласно его типу
4. **Объединение**: Результаты объединяются в единый ответ
5. **Очистка**: Временные файлы автоматически удаляются
6. **Таймаут**: Обработка архивов ограничена 300 секундами для предотвращения блокировки системы

### Безопасность архивов

- **Защита от zip-бомб**: Ограничение размера распакованного содержимого
- **Защита от path traversal**: Санитизация имен файлов в архивах
- **Контроль вложенности**: Максимум 3 уровня вложенности архивов
- **Изоляция процесса**: Распаковка в отдельном процессе с таймаутом
- **Таймаут обработки**: Принудительное завершение обработки архивов через 300 секунд

## Устранение проблем

### Частые проблемы

1. **OCR не работает**
   - Проверьте установку tesseract в Docker образе
   - Убедитесь в наличии языковых пакетов (rus+eng)

2. **Ошибки памяти**
   - Уменьшите размер файлов или архивов
   - Увеличьте лимиты контейнера
   - Уменьшите `MAX_EXTRACTED_SIZE`

3. **Таймауты**
   - Увеличьте `PROCESSING_TIMEOUT_SECONDS`
   - Уменьшите сложность входных файлов
   - Проверьте размер архивов
   - Обработка архивов автоматически завершается через 300 секунд

4. **Архивы не обрабатываются**
   - Убедитесь в наличии библиотек rarfile и py7zr
   - Проверьте размер архива и содержимого
   - Проверьте глубину вложенности
   - Обработка прекращается через 300 секунд (см. таймаут)

5. **Неполное извлечение текста**
   - DOCX: Теперь включает колонтитулы, сноски и комментарии
   - PPTX: Теперь включает заметки спикера
   - Проверьте версию API (должна быть 1.8.6+)
