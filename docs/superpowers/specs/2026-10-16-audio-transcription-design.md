# Расшифровка аудио (транскрибация) — дизайн

Дата: 2026-10-16. Источник требований: тикет tracker №52686 и обсуждение в сессии.

## 1. Цель и границы

**Цель.** Docker-образ extract-text умеет по аудиофайлу, переданному через API, возвращать расшифровку речи с тайм-кодами и разметкой «кто говорит». Потребитель — конфигурация «Управление IT-отделом 8» (1С), которая на следующем этапе сама будет забирать записи из МИКО и отправлять их в этот образ.

**Входит в эту итерацию:**

- эндпоинт `POST /v1/transcribe` (синхронный);
- модель GigaAM v3 (e2e RNN-T, русский, с пунктуацией) по умолчанию, веса запечены в образ, рантайм работает без интернета;
- тайм-коды на уровне сегментов (фраз);
- разметка говорящих по каналам стерео-записи, для моно `speaker = null`;
- второй сервис в compose из того же образа для аудио;
- документация API с примерами и инструкция по развёртыванию (критерий 7 тикета).

**Не входит:** интеграция с МИКО и очередь заданий, аудио внутри архивов, пословные тайм-коды, диаризация моно-записей, асинхронный режим с `job_id`, мультиязычные модели, GPU.

**Факты, на которые опирается дизайн:**

- Образ МИКО `excla1m/mikopbx-stt-worker` — pull-воркер без входящего API, напрямую использовать нельзя. Берём его движок: [onnx-asr](https://github.com/istupakov/onnx-asr) с GigaAM v3 (MIT).
- МИКО умеет писать звонки в стерео с раздельными каналами, формат записи mp3 ([вики МИКО](https://wiki.mikopbx.ru/general-settings)). Значит, ffmpeg в образе обязателен, а `speaker` определяется по каналу.
- onnx-asr напрямую читает только WAV, зависит от `numpy` и `onnxruntime`. `recognize(...)` принимает массив numpy; `with_vad(...)` возвращает итератор сегментов `SegmentResult(start, end, text)`.

## 2. Контракт API

`POST /v1/transcribe`, multipart/form-data. Заголовок `X-API-Key` при `AUTH_MODE=apikey` (общая зависимость `verify_api_key`). Обязателен `Content-Length`.

Поля формы:

| Поле | Обяз. | Описание |
|---|---|---|
| `file` | да | аудиофайл |
| `channel_labels` | нет | метки каналов через запятую, например `client,operator`; индекс метки = индекс канала |
| `external_id` | нет | идентификатор записи на стороне клиента, возвращается без изменений (до 128 символов) |

Ответ 200:

```json
{
  "status": "success",
  "filename": "call.mp3",
  "external_id": "rec-123",
  "duration": 183.4,
  "channels": 2,
  "model": "gigaam-v3-e2e-rnnt",
  "language": "ru",
  "text_status": "ok",
  "text": "Добрый день, компания … Здравствуйте, у меня вопрос …",
  "segments": [
    {"start": 0.52, "end": 3.10, "speaker": "operator", "channel": 1, "text": "Добрый день, компания …"},
    {"start": 3.40, "end": 5.85, "speaker": "client", "channel": 0, "text": "Здравствуйте, у меня вопрос …"}
  ]
}
```

Правила:

- `segments` отсортированы по `start`; сегменты с пустым текстом отбрасываются. `text` — тексты сегментов через пробел в хронологическом порядке.
- Стерео (ровно 2 канала): `channel` = 0 или 1, `speaker` = `channel_labels[channel]`, если метка передана, иначе `channel_0` / `channel_1`.
- Моно и записи более чем с 2 каналами (сводятся в моно): `channel = null`, `speaker = null`.
- Если лишних или недостающих меток в `channel_labels` — недостающие заменяются на `channel_N`, лишние игнорируются.
- Речь не найдена: HTTP 200, `text_status = "no_speech"`, `text = ""`, `segments = []`. При речи `text_status = "ok"`.
- `language` всегда `"ru"` (модель одноязычная), поле принимать в запросе не нужно.

Форматы: `mp3, wav, ogg, opus, flac, m4a, aac, wma, amr`. Список хранится в `settings.AUDIO_FORMATS` отдельно от `SUPPORTED_FORMATS`, поэтому `/v1/extract/*` продолжают отвечать 415 на аудио, а `/v1/supported-formats` не меняется.

Ограничения по умолчанию: размер файла не более `MAX_FILE_SIZE` (20 МБ, общий лимит), длительность не более 30 минут.

## 3. Архитектура и пайплайн

Один образ. Новый модуль [app/transcription.py](../../../app/transcription.py) (не раздуваем `extractors.py`). Эндпоинт в [app/main.py](../../../app/main.py) повторяет структуру `/v1/extract/file`: `sanitize_filename`, проверка `Content-Length` и размера, `validate_file_type`, `run_in_threadpool` под `asyncio.wait_for` с отдельным таймаутом.

Поток внутри `transcription.py`:

1. **Приём.** Загруженный файл пишется во временный файл (общие helper'ы очистки из `utils.py`).
2. **Зондирование.** `ffprobe` определяет наличие аудиодорожки, число каналов и длительность. Нет дорожки — 422. Длительность больше лимита — 413.
3. **Декодирование.** `ffmpeg` приводит звук к PCM int16, 16 кГц; стерео остаётся двухканальным, более двух каналов сводятся в моно. Вызовы через `subprocess` списком аргументов, без shell, с лимитами памяти из `utils.py` (`MAX_SUBPROCESS_MEMORY`).
4. **Распознавание.** `Transcriber` — синглтон процесса: модель GigaAM v3 и silero VAD грузятся лениво из `MODELS_DIR` один раз (под `threading.Lock`), `onnxruntime.SessionOptions` с фиксированным `intra_op_num_threads`. Для каждого канала выполняется `model.with_vad(vad).recognize(канал, sample_rate=16000)`; итератор сегментов читается в цикле, между сегментами проверяются `cancel_event` и дедлайн.
5. **Сборка.** Сегменты каналов объединяются, сортируются по `start`, собирается ответ из раздела 2.

Конкурентность: семафор `TRANSCRIPTION_MAX_CONCURRENCY` (по умолчанию 1). Если слот не освободился за `TRANSCRIPTION_QUEUE_WAIT_SECONDS`, ответ 503 с `Retry-After`.

Отмена по таймауту: при `asyncio.TimeoutError` эндпоинт выставляет `cancel_event`; рабочий поток выходит между сегментами, освобождает семафор и удаляет временные файлы в `finally`. Это закрывает известный дефект «поток продолжает работать после 504».

Безопасность ffmpeg/ffprobe: демуксер форсируется по расширению из allowlist, `-protocol_whitelist file`, `-nostdin`, без сетевых протоколов. Это блокирует playlist/concat-векторы (SSRF и чтение локальных файлов). Конкретные флаги проверяются на этапе плана.

## 4. Конфигурация (env, [app/config.py](../../../app/config.py), [env_example](../../../env_example))

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `ENABLE_TRANSCRIPTION` | `true` | при `false` эндпоинт отвечает 503, модель не грузится |
| `TRANSCRIPTION_MODEL` | `gigaam-v3-e2e-rnnt` | имя модели onnx-asr |
| `MODELS_DIR` | `/opt/models` | каталог с весами внутри образа |
| `MAX_AUDIO_DURATION_SECONDS` | `1800` | лимит длительности |
| `TRANSCRIPTION_TIMEOUT_SECONDS` | `900` | таймаут обработки (отдельно от `PROCESSING_TIMEOUT_SECONDS`) |
| `TRANSCRIPTION_MAX_CONCURRENCY` | `1` | одновременных распознаваний на процесс |
| `TRANSCRIPTION_QUEUE_WAIT_SECONDS` | `30` | ожидание слота до 503 |
| `TRANSCRIPTION_THREADS` | число ядер контейнера | потоки onnxruntime |

## 5. Docker и compose

[Dockerfile](../../../Dockerfile):

- apt: `ffmpeg`; pip: `onnx-asr[cpu,hub]` (версия фиксируется в `requirements.txt`);
- этап сборки скачивает в `/opt/models` веса GigaAM v3 e2e RNN-T и silero VAD; каталог доступен на чтение пользователю `appuser`;
- build-аргумент `GIGAAM_QUANTIZATION` (пусто = fp32, `int8`); по умолчанию fp32 (около 0,9 ГБ, качество выше). Переход на int8 решается после замера на реальных записях;
- в рантайме `HF_HUB_OFFLINE=1`, чтобы библиотека не пыталась ходить в сеть.

[docker-compose.prod.yml](../../../docker-compose.prod.yml): второй сервис `api-audio` из того же образа с `WORKERS=1`, портом 7556 и своим лимитом памяти (стартовое значение 4 ГБ, уточняется замером). Сервис документов остаётся с прежним числом воркеров и `ENABLE_TRANSCRIPTION=false`, чтобы не держать копии модели в каждом воркере. Dev-compose запускает один сервис с включённой транскрибацией.

## 6. Ошибки

Формат прежний: `JSONResponse` с `{status:"error", filename, message}` (не `HTTPException`), текст на русском, внутренние детали (stderr ffmpeg, трейсы) только в логах.

| Код | Условие |
|---|---|
| 400 | нет `Content-Length`; `external_id` длиннее 128 символов |
| 401 | нет или неверный `X-API-Key` (общая зависимость) |
| 413 | размер больше `MAX_FILE_SIZE` или длительность больше `MAX_AUDIO_DURATION_SECONDS` |
| 415 | расширение не из `AUDIO_FORMATS` или не совпадает с содержимым (`python-magic`) |
| 422 | файл пустой или повреждён; нет аудиодорожки; сбой декодирования (в том числе по лимиту памяти ffmpeg) |
| 503 | `ENABLE_TRANSCRIPTION=false`; модель не найдена или не загрузилась; очередь занята (с `Retry-After`) |
| 504 | превышен `TRANSCRIPTION_TIMEOUT_SECONDS` |

Отсутствие речи ошибкой не является (см. `text_status`, раздел 2).

## 7. Тестирование

- **Unit** (`@pytest.mark.unit`, ffmpeg и модель замоканы): слияние и сортировка сегментов двух каналов; метки каналов с `channel_labels` и без; моно и 3+ каналов дают `speaker=null`; `no_speech`; отмена по `cancel_event`; лимиты длительности; разбор параметров.
- **Контрактные** (`@pytest.mark.integration`, `TestClient` с подменой `Transcriber`): 200, 400, 401, 413, 415, 422, 503, 504 и форма ответа.
- **Smoke с настоящей моделью** (`@pytest.mark.slow`, пропускается, если `MODELS_DIR` пуст): короткая русская запись в `tests/audio/` (подкаталог, чтобы `TestAllRealFiles` не прогнал её через `/v1/extract/*`; при реализации проверить, что тест не обходит подкаталоги) — непустой текст и неубывающие тайм-коды; стерео собирается в тесте из двух моно-клипов и проверяется разметка говорящих.
- CI: шаг `docker build` включает скачивание весов; проверить, что у CI есть доступ к HuggingFace, иначе использовать кэш слоя или зеркало.
- Порог покрытия (`--cov-fail-under`) не снижаем.

## 10. Открытые вопросы (не блокируют начало реализации)

1. Порядок каналов в стерео-записях МИКО (какой канал клиент, какой оператор) — подтвердить на реальных входящей и исходящей записях; нужны образцы.
2. fp32 против int8: замерить WER и память на реальных звонках.
3. Параметры VAD (`threshold`, `min_silence_duration_ms`, `max_speech_duration_s`) подобрать на телефонных записях; в onnx-asr значения по умолчанию в документации не указаны.
4. Offline-загрузка silero VAD через параметр `path` в `load_vad` — проверить на сборке, при необходимости добавить явную загрузку файла в `MODELS_DIR`.
5. Лимиты длительности и таймаут (30 мин / 900 с) — сверить с измеренным RTF на целевом сервере.
6. Доступ CI к HuggingFace при сборке образа.
